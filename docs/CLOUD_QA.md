# Приёмка облачных сохранений

Локальный P0-цикл уже проверен, но SAVE-01 пока открыт. Ни memory roundtrip,
ни восстановление модели после respawn не считаются облачным повторным входом.

## Подготовленная сборка

Обычный `default.project.json` оставляет Studio в MemoryPreview. Исходник Storage
больше не нужно переключать перед тестом. После подготовки отдельной тестовой
experience можно собрать QA-копию:

```bash
python3 scripts/build_cloud_test.py --universe-id ВАШ_UNIVERSE_ID --place-id ВАШ_PLACE_ID
```

Появятся `build/cloud-test.project.json` и `build/cloud-test.rbxlx`. Исходники и
основной проект не меняются. Скрипт ничего не публикует и не обращается к Roblox.
`--check` проверяет параметры без сборки. Числа 123/456 используются только
в локальных тестах генератора и не являются настроенной облачной целью.

QA-проект использует loopback-порт 34873. Все `$path` абсолютные, поэтому проект
корректно собирается и из каталога build. Для синхронизации:

```bash
export PATH="$PWD/.tools/bin:$HOME/.rokit/bin:$PATH"
rojo serve build/cloud-test.project.json --address 127.0.0.1 --port 34873
```

Открыть в Studio именно опубликованный тестовый Place и подключить Rojo к
34873. Это сохраняет реальные GameId/PlaceId открытого Place. Локально открытый
`.rbxlx` с нулевыми IDs намеренно блокируется для облачного режима. Подключение
обычного проекта на 34872 возвращает обычные настройки MemoryPreview.

## Изоляция

- Для Studio QA должны совпасть разрешённые Universe ID и Place ID. При нулевых,
  неизвестных или несовпадающих IDs адаптер не обращается к DataStore и не даёт
  редактируемый дефолт.
- Namespace Studio QA: `NeighborhoodFixer_P0_StudioQA_v1`.
- В настоящем сервере `IsStudio=false` всегда используется прежний namespace
  `NeighborhoodFixer_P0_v1`, независимо от настроек разработки. Миграции namespace нет.
- При ошибке облачной записи перехода в память нет.
- Studio QA и настоящий Roblox-клиент используют разные namespace. Их прогресс
  нельзя сравнивать как одну запись. Для проверки Roblox-клиента отдельно пройти
  тот же цикл внутри тестовой experience.

Roblox использует общие DataStore для мест одной experience. Поэтому требуется
**отдельная тестовая experience**, а не дополнительный Place внутри боевой.
Studio API Services включать только там. Основание: [официальная документация
DataStore и доступа Studio](https://create.roblox.com/docs/cloud-services/data-stores).
Публикация и изменение доступа к API требуют отдельного поручения пользователя.

## Проверка на настоящем backend

1. Проверить положительные UserId/GameId/PlaceId, совпадение QA-настроек и
   `Storage.preview=false`, `Storage.blocked=nil`. В Home должен быть облачный
   режим; ошибка загрузки не должна давать нового персонажа с редактируемым $0.
2. Пройти покраску, сдать один раз, купить растение, установить его. Записать
   баланс, instanceId, housing revision и локальную позу в приватный QA-отчёт.
3. Корректно остановить Play, дождаться release. Запустить снова в том же
   тестовом Place: баланс/владение/поза/обучение должны восстановиться.
4. Повторить запрос покупки и сдачи: дополнительного списания/награды нет.
5. Переместить предмет, убрать на склад, снова установить и повторить вход.
6. Проверить отказ при отключённом API и конфликте двух сессий: нет дефолтного
   редактируемого профиля, чужая или просроченная сессия не пишет.
7. Для настоящего Roblox-клиента отдельно проверить выход/перезаход в приватной
   тестовой experience. Studio-run не выдавать за эту проверку.

Не редактировать и не очищать production-записи ради тестов. Ключ, metadata,
lease/fence и протокол повторов описаны в [PROFILE_STORAGE.md](PROFILE_STORAGE.md).
Пока эти сценарии реально не выполнены, SAVE-01 не закрывается.
