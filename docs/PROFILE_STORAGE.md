# Профиль, сессия и первый вход

## Текущий игровой срез

Главный проект `default.project.json` запускает `ProfileService`: загрузка
профиля → личная комната → персонаж → HUD долларов. Одна серверная сессия
владеет всем профилем. Кнопка Home/Дом возвращает живого владельца на его
точку появления; клиент не передаёт владельца или координаты назначения.
Повторы ограничены двумя секундами. Проверка границ комнаты возвращает
постороннего персонажа в его собственный дом. Это контроль доступа, а не
обещание скрыть геометрию от модифицированного клиента.

Комнаты размещаются на 16 отдельных участках компактной сетки 4×4. Номер участка
не сохраняется как мировая позиция: профиль хранит шаблон комнаты и его версию.
Шаблон содержит четыре стены, вход шириной 6 studs, спавн, кровать, стол и свет.
Это собственная базовая геометрия без внешних моделей/скриптов.

Jobs/Painting, магазин и редактор подключены к этому же профилю. Награда,
покупка и расстановка проходят через один ProfileStore; локальный полный
цикл проверен в Studio. Облачная приёмка ещё не выполнена.

## Два явно разделённых режима

Обычный проект задаёт `ServerStorage.DevelopmentSettings.StudioDataStoreTest=false`:
MemoryPreview включается **только** при `RunService:IsStudio()`. На экране
написано, что прогресс существует до остановки сервера. Симулированные Studio
ID ≤0 получают отдельные положительные ключи только в этом режиме.

Для облачной приёмки подготовлен отдельный генератор QA-сборки с явными
Universe/Place ID и отдельным namespace. Неправильные/нулевые IDs блокируют
обращение к данным. В production MemoryPreview невозможен; ошибка DataStore
не создаёт новый редактируемый профиль. Подготовка и незакрытые сценарии:
[CLOUD_QA.md](CLOUD_QA.md). Эта задача не публикует игру и не включает API Services.

DataStore: `NeighborhoodFixer_P0_v1`, scope по умолчанию, ключ `player:<UserId>`.
Не переименовывать namespace без отдельной миграции. Одна запись:

```text
recordVersion = 1
profile = единый Profile schemaVersion 2
fence = монотонный номер владельца
leaseOwner = уникальный GUID сессии или пустая строка после release
leaseUntil = Unix time; 0 после release
commitId = token:sequence последней подтверждённой операции координатора
```

Запись относится к owner UserId через userIds UpdateAsync; существующая metadata
сохраняется. Весь профиль, включая деньги/собственность/квитанции, записывается
одновременно. Серверные секреты и блокировки не реплицируются клиенту.

## Контракт координатора ProfileStore

`load` атомарно читает и захватывает lease через UpdateAsync. Только реальный
отсутствующий ключ создаёт `Profile.new`. Повреждённая запись, чужой активный
lease или неизвестная схема не заменяются дефолтом.

`read` возвращает глубокую копию только в Ready, при действующем lease и вне
незавершённой операции. `transact` применяет чистую функцию к копии и повторно
проверяет профиль. Изменение становится доступным только после подтверждения
записи. Один ключ имеет одну активную операцию; конкурирующая работа отклоняется,
пока запрос или его безопасный повтор не завершится. Другие игроки независимы.

При неизвестном исходе сохраняется точный pending snapshot/commitId. Новая
мутация блокируется; `retry` подтверждает уже записанный commitId либо записывает
исходный snapshot после проверки lease/fence/revision. Функция мутации повторно
не вызывается. CAS callback может быть повторён самим UpdateAsync — он не имеет
побочных эффектов снаружи создаваемой записи.

Для награды `transact` принимает серверный guard: перед новой записью заново
проверяются текущий персонаж, жизнь, дистанция/видимость и nonce работы. Если
персонаж умер во время ожидания UpdateAsync, неподтверждённая выплата отменяется.
Уже записанный commitId подтверждается даже после смерти: это квитанция прошлого
commit, а не новая награда. Оба случая покрыты отдельными тестами.

Lease — 120 секунд; heartbeat — каждые 30. Истёкшая сессия не возрождается.
Захват другим сервером увеличивает fence, который остаётся после release:
старый владелец не может записать даже после выхода нового владельца.

`PlayerRemoving` и `BindToClose` пытаются разрешить pending запись и освободить
lease с ограниченным ожиданием. Повторы сети ограничены, с backoff и jitter.
Если Roblox завершит сервер до release, следующий вход может ждать истечения
lease; безусловная запись поверх чужого состояния не выполняется.

## Ошибки и жизненный цикл

При начальной или поздней успешной загрузке один `finalizeReady` создаёт комнату
и подтверждённый HUD. Спавн запрашивается отдельно: если загрузка персонажа
совпала с сохранением, запрос остаётся pending и повторяется после Ready.
Флаг spawning предотвращает две одновременные загрузки персонажа. Отложенная
реакция на смерть не заменяет уже появившийся новый Character.

15 тестов ProfileStore проверяют acquisition/конфликты, ошибки до/после commit,
повторы, release, stale revision, истечение lease, reentrant вызовы и совместную
запись покупки/денег. 2 lifecycle-сценария выполняют настоящий модуль сервиса
с детерминированными внешними заглушками. Они воспроизвели оба дефекта до
исправления и проходят после него; это не эмуляция всех Roblox API и не Play.

Официальные основания:
[session locking, порядок повторов и неизвестные исходы записи](https://create.roblox.com/docs/cloud-services/data-stores/player-data-purchasing),
[UpdateAsync](https://create.roblox.com/docs/reference/engine/classes/GlobalDataStore#UpdateAsync).
