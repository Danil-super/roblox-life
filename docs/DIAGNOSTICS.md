# Серверная диагностика P0 — OBS-01

Локальная часть §11.6 GDD: журнал подтверждённых изменений профиля в Roblox
Output. Зависимостей, HTTP-запросов и внешней аналитики нет.

Журнал отвечает на три вопроса:

1. Подтвердилась ли выплата/покупка и как изменились доллары/XP?
2. Сохранились ли установка, перенос, склад и завершение обучения?
3. Был ли повтор новой операцией или повторной публикацией прежней ревизии?

`ProfileService.publish` читает подтверждённый `ProfileStore.read()` и передаёт
его в `Diagnostics.observe`. Чистый `Domain/ProfileChanges` сравнивает компактные
копии состояния. Первая загрузка задаёт baseline и не воспроизводит историю.
Одинаковая/старая ревизия не создаёт событие. Новый checkpoint без значимых
изменений также молчит. При Uncertain `read()` недоступен; журнал появляется
после подтверждения исходного intent при recovery.

Одна строка JSON — один пакет изменений подтверждённой ревизии:

```json
{"schema":1,"event":"profile_change","trace":"12345678-1234-1234-1234-123456789abc","entry":"confirmed","revision":7,"dollarsDelta":250,"xpDelta":50,"changes":[{"event":"job_completed","subject":"paint-tutorial-v1","amount":250,"xp":50},{"event":"onboarding_step","subject":"BUY"}],"omitted":0}
```

Ревизия примера условная. `amount` положителен и означает размер награды или
цену купленного экземпляра; знак списания находится в `dollarsDelta` пакета.
Цена берётся из сохранённого `paidDollars`, награда — из квитанции, а не из UI.
`job_completed` требует сохранённой квитанции.

События: `job_accepted`, `job_completed`, `job_abandoned`, `onboarding_step`,
`onboarding_completed`, `furniture_purchased`, `furniture_placed`,
`furniture_moved`, `furniture_stored`. Прежние `profile_load`,
`profile_recovery`, `profile_failure` сохранены; к ним добавлена версия схемы.

На пакет выводятся максимум восемь изменений; `omitted` показывает количество
остальных. Инвентарь ограничен прежними 256 экземплярами. Не создаются записи
о каждом штрихе, наведении, sync и heartbeat без значимых изменений.
Сбой кодирования/вывода перехватывается; профиль, публикация HUD и игровая
операция продолжают работу. Потерянное событие не повторяется после сбоя sink.
Это best effort диагностика, не финансовый журнал и не гарантия доставки.

В `trace` используется случайный GUID текущего серверного контекста;
после нового входа он другой. Имена, UserId, requestId, jobId, workId,
itemInstanceId, operationId, координаты и содержимое запросов не выводятся.
Внутренние ID используются только для сравнения и не попадают в payload.
`subject` ограничен конфигурацией контрактов/каталога и шагами обучения;
неизвестный код заменяется на `unknown`. Причины ошибок — фиксированный
список, неизвестная причина становится `Other`; сырая ошибка не печатается.
Несколько одинаковых предметов различаются только ревизией и контекстом.

## Разбор проблемы

В Studio откройте Output и найдите `profile_change`. По `trace` соберите
операции одного входа, по `revision` проверьте порядок. При жалобе на деньги
смотрите `dollarsDelta`, затем `job_completed`/`furniture_purchased`.
При проблеме мебели — `furniture_*`; при восстановлении — `profile_failure`
и `profile_recovery` с тем же trace. Отсутствие строки само по себе не
доказывает отсутствие записи: sink может отказать или история Output очиститься.
Не выдавайте компенсацию автоматически на основании одного журнала.

`HttpService:JSONEncode` работает без включения HTTP Requests:
[официальная документация](https://create.roblox.com/docs/reference/engine/classes/HttpService#JSONEncode).

## Проверки и границы

`ProfileChanges.test.luau` использует настоящие Jobs/Economy/Furniture:
награда/повтор, покупка, установка/перенос/склад, отмена, DONE, baseline,
копирование поз, старая ревизия, независимость, лимит пакета и allowlist.
`Diagnostics.test.py` исполняет настоящий модуль с детерминированной границей
HttpService/Output: схема, приватность, сбой JSON/print и повторная публикация.
Настоящий ProfileStore отдельно проверяется при записи с неизвестным исходом:
до подтверждения строк нет, после retry — одна, повтор publish не дублирует её.

Одиночный Play 2026-11-05 в одной Studio подтвердил реальный цикл без
QA-баланса: учебная покраска мышью → $250/50 XP → Touch-покупка растения
за $180 → установка/DONE → перенос → склад → повторная установка →
принятие/отмена Mint. Официальный `get_console_output` вернул девять
`profile_change` с уникальными ревизиями и одним trace: приняты два заказа,
завершён один, отменён один, куплен один предмет, две установки, один перенос,
один склад, один DONE; сумма изменений $70/50 XP. Ни один платёж не дублировался.
Повторное открытие Inventory/Jobs не увеличило число пакетов.

При автоматическом переходе после повторной установки обнаружен лишний
открытый редактор без отправленного intent: закрыт обычным Cancel, сохранённые
предмет/деньги не изменились. Первые проверки перехода к заказу остановились;
перед продолжением подтверждена видимость панелей. После Accept Jobs закрыт
самой игрой — для отмены панель открыта заново. Ошибки маршрута теста не
засчитаны успешными шагами и не использованы как доказательство сбоя сохранений.

В следующем этапе BUILD-UI-QA-08 причина лишнего входа воспроизведена:
проверочный сценарий нажимал скрытую Jobs, а фактический Activated получала
видимая Inventory/Place. Установка сама закрывала редактор правильно.
Добавлены preflight ввода и повторяемый маршрут: docs/LOCAL_QA.md.

отказа и критические отказы антиэксплойт-проверок ещё требуют отдельного

многоклиентская приёмка этим этапом не подтверждаются.
