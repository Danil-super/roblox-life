# «Мастер на районе» / Neighborhood Fixer
## Game Design Document + техническое задание для Codex

**Версия:** 0.7 (рабочая, не финальная)  
**Дата:** 2 ноября 2026 г.  
**Статус:** решения 1–65 зафиксированы; детализированы игровой старт, UI, обучение, интерактивная покраска, базовая комната и архитектура первого вертикального среза; баланс, ассеты и техническая интеграция MCP требуют проверки.  
**Назначение:** единый источник требований для проектирования, разработки и тестирования Roblox-игры. Версия 0.7 сохраняет решения 1–59 и добавляет согласованные решения 60–65, спецификации экранов/сцен/состояний и пошаговый инженерный backlog для Codex.  

> Обозначения: **[УТВЕРЖДЕНО]** — выбор пользователя; **[ПРЕДЛОЖЕНИЕ]** — инженерное решение для проверки; **[ОТКРЫТО]** — решение ещё не принято. Запрещается выдавать предложения за утверждённые требования.

# 1. Общее описание игры

## 1.1. Концепция [УТВЕРЖДЕНО]

Жанр: многопользовательский симулятор жизни, работы и развития в открытом городском районе. Игрок начинает с бесплатной комнаты в общежитии и минимального набора инструментов. Выполняя заказы жителей, он получает игровую валюту ($), опыт и репутацию, покупает инструменты и транспорт, арендует или приобретает жильё, оформляет интерьеры, открывает собственную мастерскую, взаимодействует с друзьями и обменивается подарками.

**Главная дизайнерская цель:** заработок — средство для расширения свободы, а не самоцель. Покупка нового имущества должна давать ощущение изменения образа жизни, а развитие профессии — новые игровые действия, а не только увеличение чисел.

Референс игрового цикла: Taxi Boss; копирование игровых ассетов, карт, брендинга или чужого кода не допускается.

## 1.2. Циклы игры

**Короткий:** выбрать заказ → добраться до объекта → подготовиться → выполнить действия → проверить результат → получить награду.

**Средний:** заработать → выбрать вложение → приобрести инструмент/транспорт/мебель → открыть новый вид или уровень задания.

**Длинный:** развить навыки и репутацию, приобрести недвижимость, создать интерьер, открыть и оформить мастерскую, получить доступ к комплексным проектам, коллекционировать вещи и играть с друзьями.

## 1.3. Платформы, аудитория, визуальный стиль [УТВЕРЖДЕНО]

- ПК, смартфоны, планшеты; интерфейс и действия разрабатываются под мышь/клавиатуру и сенсорное управление с самого начала.
- Международная аудитория; первичные языки интерфейса — английский и русский; строки вынести в локализационные ресурсы.
- Современная стилизованная графика: качественное освещение и материалы, опрятные архитектурные объекты и мебель, умеренная детализация.
- Вымышленный город с живыми декоративными элементами: движение NPC-автомобилей, пешеходы, светофоры и общественный транспорт. Основная роль окружения — визуальная атмосфера, а не отдельный симулятор городского управления.
- Ориентир: 12–16 участников на сервер. Точный лимит устанавливается после тестирования на мобильных устройствах.

# 2. Зафиксированные решения по игровым системам

| Область | Решение |
|---|---|
| Основная деятельность | Симулятор жизни, где профессии и заказы — главный источник заработка на старте |
| Начальные профессии | Покраска, сборка мебели, перевозка, бытовой ремонт |
| Будущие профессии | Уборка, электрика, сантехника и другие, без необходимости переписывать ядро |
| Мини-игры | Не просто удержание кнопки: есть необходимые подготовительные этапы; сложность растёт вместе с квалификацией |
| Заказы | Процедурная сборка из подготовленных шаблонов, объектов и правил |

# 3. Бытовые взаимодействия

## 3.1. Общий принцип [УТВЕРЖДЕНО]

Игрок может взаимодействовать с предметами дома, но игра не требует постоянного контроля голода, сна, жажды или посещения туалета. Нельзя блокировать заказы, передвижение или развитие за отказ от бытовых действий.

## 3.2. Предлагаемые действия [ПРЕДЛОЖЕНИЕ]

- **Кухня:** взять продукты → выбрать рецепт → короткая мини-игра → получить блюдо → съесть/поставить на стол/подарить, если механизм подарков это позволяет.
- **Ванная/туалет:** подойти к интерактивному объекту → запустить короткую анимацию с приватностью → сразу вернуть управление. Без чрезмерно натуралистичных сцен.
- **Кровать/диван:** лечь или сесть, выйти из анимации по действию игрока; без ожидания восстановления обязательной энергии.
- **Мебель и техника:** разумный набор взаимодействий (сесть, включить свет, открыть шкаф, пользоваться компьютером) для ощущения живого пространства.

Возможные косметические или небольшие временные бонусы за еду — **[ОТКРЫТО]**; базовая экономика не должна зависеть от еды.

# 4. Универсальная система заказов

## 4.1. Типы заказов

- **Быстрые:** одна профессия и короткий маршрут, начальный доступ.
- **Стандартные:** несколько шагов одной профессии, больше инструментов и вариантов.
- **Комплексные:** несколько профессий, план выполнения и возможность кооператива; прогресс сохраняется.

Ориентиры времени для проверки в прототипе: простое действие — 15–45 секунд; короткий заказ — 2–4 минуты; стандартный — 5–10 минут; комплексный — 10–20 минут. Это проектные гипотезы, не финальный баланс.

## 4.2. Источники заказов

- Приложение **Jobs** на внутриигровом телефоне: список, сортировка, требования, адрес, сумма и этапы.
- Терминал/доска в мастерской или специальные точки в городе: комплексные контракты.
- Предложения не должны ссылаться на недоступные помещения, неисправные маркеры или отсутствующие объекты.

## 4.3. Процедурная сборка [УТВЕРЖДЕНО + ПРЕДЛОЖЕНИЕ реализации]

Генератор выбирает только из валидированных ассетов и шаблонов:

1. Доступную планировку и рабочее пространство с идентификатором.
2. Тип объекта, его стартовое состояние, свойства и точки взаимодействия.
3. Профессиональные действия и их зависимости.
4. Условия: сложность, квалификация, инструменты, материалы, оценка качества.
5. Параметры заказчика: допустимые цвета, бюджет, предпочтения, дополнительные требования.
6. Награду на сервере с учётом норматива длительности, объёма работы, сложности и качества.
7. Уникальный идентификатор заказа и seed генерации для диагностики/восстановления.

**Ограничение:** в MVP не генерировать геометрию квартир с нуля. Использовать валидные планировки, меблировку и наборы объектов с готовыми слотами/точками установки. Это позволяет проверить достижимость и избежать пересечений мебели.

## 4.4. Зависимости шагов

Проект представляется графом зависимостей (DAG), а не одним жёстким списком. Пример:

- Привезти материалы → подготовить и покрасить стены.
- Покрасить стены → установить мебель вдоль окрашиваемой стены.
- Починить прибор → протестировать его.
- Всё выполнено → итоговый осмотр и приёмка.

Часть независимых задач доступна одновременно для совместного выполнения.

## 4.5. Состояния заказа

`Offered → Accepted → Travelling → InProgress → ReadyForInspection → Completed`

Дополнительные состояния: `Abandoned`, `Expired` (для необязательных предложений), `Paused` (сохраняемые комплексные), `FailedValidation` (внутренняя ошибка, не наказание игрока).

Любой переход состояния проверяется сервером; награда выплачивается однократно, идентификатор операции сохраняется для защиты от повторного начисления.

## 4.6. Проверка генератора

- Генерировать большие наборы тестовых заказов с фиксированными seed.
- Проверять наличие ассетов, инструмента/аренды, корректность точек входа и установки.
- Проверять, что граф зависимостей ацикличен и каждый этап достижим.
- Для каждой сложности должен существовать хотя бы один заказ, доступный игроку соответствующего уровня.
- При ошибке генерации использовать безопасный резервный шаблон, логировать ошибку, не назначать сломанный заказ.

# 5. Общая система интерактивных работ

## 5.1. Принципы [УТВЕРЖДЕНО]

Сложность возрастает за счёт новых этапов, инструментов и самостоятельного выбора правильного действия, а не только длительности удержания кнопки. Одно простое действие — ориентировочно 15–45 секунд.

## 5.2. Базовые интеракции [ПРЕДЛОЖЕНИЕ]

Компоненты интерфейса и игрового мира:

- `Inspect`: осмотр объекта или дефекта.
- `Select`: выбор инструмента/материала/детали.
- `Prepare`: подготовка площадки или оборудования.
- `DragOrSwipe`: движение валиком, очистка, перемещение в пределах разрешённой области.
- `SnapPart`: установка детали в валидную позицию.
- `TimedAction`: короткое удержание или последовательность с обратной связью.
- `Verify`: проверка результата.

Код мини-игр отделён от конфигураций конкретной профессии: общие входы, состояние шага, завершение, оценка, локализованные подсказки.

**Безопасность:** клиент отправляет намерения и ограниченные результаты действий, сервер валидирует допустимость, порядок шагов и темп прогресса. Не доверять сообщению `jobFinished=true` или `reward=...` от клиента.

## 5.3. Профессия «Покраска» [УТВЕРЖДЕНО: поэтапная]

**Новичок:** получить заказ → осмотреть стену → подготовить рабочее место (если нужно) → выбрать правильный цвет → работать валиком по сегментам поверхности → проверить покрытие → сдать работу.

**С повышением квалификации:** укрытие мебели, подготовка/ремонт дефектов, грунтовка, несколько слоёв, дополнительные цветовые требования и сложные поверхности.

**Управление:** мышью — движение по поверхности; на телефоне — свайпы по подсвеченной зоне, без необходимости попадать в мельчайшие элементы. Прогресс видим на стене, а не только в полосе процентов.

**Качество:** соответствие цвету, покрытие обязательных сегментов, выполнение необходимых подготовительных шагов. На первом уровне допустимы подсказки и практически полная выплата даже при ошибках.

## 5.4. Профессия «Сборка мебели» [УТВЕРЖДЕНО: действия с деталями]

**Начальные сценарии:** табурет, тумба, полка; далее шкаф, стол, сложные комплекты.

**Шаги:** принять комплект → распаковать → открыть схему → выбрать деталь → установить на направляющий узел → использовать подходящий инструмент/крепёж → проверить устойчивость → сдать заказ.

На объекте должна изменяться реальная визуальная сборка: детали появляются на своих местах по мере выполнения. Не симулировать полный физический конструктор и сотни свободных Rigidbody в MVP; использовать точки привязки и подготовленные состояния модели.

**Качество:** правильная последовательность и детали, число ошибок, итоговая проверка.

## 5.5. Профессия «Бытовой ремонт» [УТВЕРЖДЕНО: широкая профессия]

**Стартовые прототипы (предложение):** расшатанный стул, неисправная дверь, светильник, бытовой прибор. Электрика/сантехника как большие специализированные системы — позже.

**Шаги:** осмотр → диагностика → выбор нужной детали/инструмента → ремонт через короткую мини-игру → функциональная проверка → сдача.

У новичка источник неисправности подсвечен; у опытного игрока нужно выбирать между несколькими возможными причинами. Технические детали не должны быть опасными инструкциями для настоящего ремонта электричества: это игровые условности.

**Качество:** правильно выявленная игровая неисправность, комплектность действий, успешная проверка.

## 5.6. Профессия «Перевозки» [УТВЕРЖДЕНО: расширенная логистика, простое управление]

**Шаги:** принять заказ → ознакомиться с габаритами и местом доставки → подобрать свой или арендованный транспорт → забрать груз → погрузить в специальные слоты → доставить по маршруту → выгрузить → подтвердить доставку.

Физическое действие по переноске должно ощущаться реальным, но предметы при загрузке фиксируются в слотах, а не свободно прыгают в кузове. Вместимость и тип транспорта ограничивают допустимые грузы. Для велосипеда — небольшие посылки, для крупной мебели — аренда фургона/грузового транспорта.

**Качество:** сохранность груза, выполнение обязательных этапов, при необходимости своевременность; не наказывать за сбои управления на мобильных устройствах. Введённые временные ограничения не должны быть агрессивными.

## 5.7. Оценка результата

Награда рассчитывается только на сервере. Рекомендуемая схема:

`Reward = BasePay(orderTemplate, scope, difficulty) × QualityMultiplier × EventMultiplier`.

Точные коэффициенты **[ОТКРЫТО]**; минимальная гарантированная выплата по обучающим и большинству обычных заказов, мягкие санкции для новичков. Не допускать отрицательный баланс при обычных игровых ошибках.

# 6. Комплексные заказы и совместная игра

## 6.1. Комплексные контракты [УТВЕРЖДЕНО]

Пример: реконструкция квартиры из готовой планировки, где проект состоит из доставки материалов, подготовки и покраски, сборки мебели и ремонта оборудования.

- Один игрок может пройти заказ целиком.
- Команда может одновременно брать независимые этапы.
- После завершения — оценка, награда, опыт, экран сравнения состояния помещения «до/после» и запись проекта в портфолио (портфолио — предложение).
- Для сравнения «до/после» можно хранить детерминированные снимки состояния или визуально реконструировать оба состояния без обязательного серверного хранения изображений.

## 6.2. Кооператив [УТВЕРЖДЕНО, включая 57-В]

- Игрок создаёт команду и приглашает участников.
- Команда выбирает совместный контракт.
- Участники видят доступные этапы и самостоятельно выбирают задачи.
- Сервер фиксирует проверенный вклад (выполненные единицы работ; не время бездействия).
- Выплата пропорциональна вкладу, но правило для очень маленького вклада и командных накладных расходов **[ОТКРЫТО]**.
- Если ведущий участник выходит, роль лидера передаётся одному из оставшихся участников по детерминированному правилу (например, первый присоединившийся). Остальные могут продолжать; ушедшего нельзя лишать уже сохранённого подтверждённого вклада. Если выходят все, комплексный заказ переводится в `Paused`, а проверенные этапы сохраняются.

**Техническая осторожность:** базовый MVP кооператива ограничить участниками одного игрового сервера. После выхода последнего участника задача ставится на паузу. Продолжение на новом сервере, передача роли лидера между серверами и разрешение одновременных входов требуют отдельной стратегии согласования состояний и не входят в первый вертикальный срез.

## 6.3. Отключение и пауза [УТВЕРЖДЕНО]

- Обычный заказ: допускается отмена/перезапуск без серьёзных санкций; дисконнект не приравнивается к намеренной порче работы.
- Комплексный заказ: сохранять seed генерации, шаблон, выполненные этапы, условия, права команды и проверенные результаты.
- При повторном входе предлагать продолжить проект при технической возможности.
- Для кооператива **[УТВЕРЖДЕНО: 57-В]**: передача лидерства при выходе лидера; когда не осталось участников — пауза с сохранением. Точные сроки хранения паузы и перезаход между серверами определяются на этапе кооператива.

# 7. Жильё и редактор интерьеров

## 7.1. Прогресс [УТВЕРЖДЕНО]

Бесплатная стартовая комната в общежитии → арендованные квартиры → собственные квартиры/дома; новые варианты отличаются планировкой, размещением и возможностями оформления. Существование недвижимости не зависит от срока отсутствия игрока.

## 7.2. Аренда [УТВЕРЖДЕНО; детали — предложение]

- Время аренды расходуется **только при активном присутствии игрока в игре**. При офлайне счётчик не идёт, долги не начисляются.
- Стартовая комната бесплатна и не изымается.
- По окончании аренды **[УТВЕРЖДЕНО: 56-Б]** игрок получает уведомление и льготный период для продления, оплачиваемый **только активным онлайн-временем**. По завершении льготного периода квартира освобождается логически, а мебель и персональные данные интерьера переводятся в безопасное хранилище; жильё общежития остаётся доступным. Длительность льготного периода — настраиваемая гипотеза (начать с 60 минут активного времени) и подлежит тестам.
- Мебель, купленные отделочные материалы (в границах правил экономики) и инвентарь не исчезают при смене жилья или завершении аренды.
- Для сохранения объектов использовать модели размещения и метаданные, а не полные копии каждой детали мира в DataStore.

## 7.3. Режим строительства [УТВЕРЖДЕНО: вариант Б]

Игрок может размещать, поворачивать и удалять собственную мебель, менять цвет/отделку стен и пола, создавать/убирать **разрешённые** межкомнатные перегородки и размещать двери. Несущую структуру и внешнюю оболочку здания в первой версии менять нельзя.

**Рекомендуемые ограничения:**

- У предметов есть габариты, категории поверхностей, точки крепления и требования к коллизиям.
- Перед установкой показан призрачный предпросмотр и валидность позиции.
- Нельзя перекрывать обязательные входы/точки появления игроков или оставлять неиспользуемые помещения без требуемого доступа.
- **[УТВЕРЖДЕНО: 55-В]** Переключение между привязкой к сетке и свободной установкой мебели. Оба режима подчиняются общим ограничениям: допустимые зоны, положение относительно пола, стены и соседних предметов. Перегородки и дверные проёмы размещаются только в разрешённых строительных зонах/по строительной сетке.
- Расстановка проверяется и хранится на сервере, клиент отправляет запрошенные трансформации.
- Предметы и интерьеры имеют стабильные ID, версионирование и операции отмены (последнее — предложение).
- Указание владельца и разрешений: гости могут посещать и взаимодействовать; редактирование без разрешения владельца запрещено.

## 7.4. Интерьеры заказчиков [УТВЕРЖДЕНО]

Набор подготовленных типовых планировок, состояние объектов определяется конфигурацией заказа. Система должна позволять отображать несколько вариантов одной планировки, не создавая уникальную геометрию для каждого задания.

# 8. Транспорт и город

## 8.1. Город [УТВЕРЖДЕНО]

Первый насыщенный район с жилыми домами, общежитием, магазинами, мастерской, точками заказов, остановками, дорогами, парковками и несколькими узнаваемыми ориентирами. Город вымышленный, визуальный стиль единый. NPC-трафик, пешеходы, светофоры и общественный транспорт создают ощущение жизни; их симуляция должна быть бюджетной по ресурсам.

## 8.2. Перемещение [УТВЕРЖДЕНО]

- **[УТВЕРЖДЕНО: 59-В]** При первом входе игрок выбирает велосипед или электросамокат. В начале оба транспорта дают сопоставимые скорость, доступность маршрутов и возможности, чтобы выбор был эстетическим, а не наказанием за незнание меты. Физическая выдача одного экземпляра и сохранение выбора выполняются сервером.
- Затем — личные машины с разной вместимостью и полезностью для доставки.
- Для груза допускается аренда подходящей техники без необходимости сразу покупать дорогой автомобиль.
- Управление автомобилем — полуреалистичное, но доступное. Сенсорные кнопки не перекрывают экран задания.
- Мягкая экономика: топливо, мойка, обслуживание, ремонт и улучшения без частых «налогов на игру».

# 9. Социальные системы и подарки

## 9.1. Подарки — этапность [УТВЕРЖДЕНО]

**Первый релиз механики подарков:** игрок покупает вещь из разрешённого внутриигрового каталога в подарок другому игроку **на том же сервере**, находящемуся онлайн. Получатель видит предложение и принимает/отклоняет его. Вещь выдаётся один раз, после серверного подтверждения цены и резервирования/списания внутриигровых долларов. Отказ/таймаут — безопасный возврат суммы по идемпотентной операции.

**После стабилизации:** (1) офлайн-доставка подарков по Roblox UserId, (2) дарение уже принадлежащих игроку предметов (декор, мебель, одежда, инструменты, автомобили). **Нельзя предполагать атомарную транзакцию между двумя DataStore-ключами:** нужна модель резервирования/escrow, журнал состояний, идемпотентность, согласование после сбоев и восстановление/компенсация. Подробный протокол проектировать отдельным этапом.

**Не входит автоматически:** передача Robux, внешних аватарных предметов Roblox, наличных долларов между игроками или вещи из чужих игр.

## 9.2. Ограничения безопасности [ПРЕДЛОЖЕНИЕ]

- Уникальный ID подарочной транзакции и её состояние.
- Проверка владельца, типа предмета, наличия средств, лимитов и получателя на сервере.
- Антидублирование и идемпотентное повторение при сетевых ошибках.
- Предотвращение случайной передачи ценных предметов: подтверждение + ясный текст.
- Лимиты и журналы событий; ручные способы расследования спорных обменов.

# 11. Техническая архитектура для Codex

## 11.1. Среда разработки [ПОЖЕЛАНИЕ ПОЛЬЗОВАТЕЛЯ, требует фактической проверки]

- Ubuntu, Visual Studio Code, OpenAI Codex.
- Roblox Studio через Vinegar, запуск Roblox-клиента для тестирования через Sober — в соответствии с ранее выбранным пользователем подходом; фактическую совместимость компонентов следует проверить на его машине.
- Luau, Rojo 7, Rokit, Selene, StyLua, Luau Language Server, Git/GitHub.
- Встроенный Roblox Studio MCP — для инспекции и редактирования игрового мира/сцены и тестирования **при подтверждённой совместимости с этой установкой**.
- Официальная документация Roblox на текущий момент приводит способы запуска MCP для Windows и macOS, но не документирует Linux/Vinegar как поддерживаемый вариант. Интеграция с Codex CLI предусмотрена, однако именно связку Ubuntu + Vinegar необходимо проверять практически: https://create.roblox.com/docs/studio/mcp.
- **Этап 0 / обязательная проверка MCP (не эквивалент доказанной поддержке Ubuntu/Vinegar):** открыть Roblox Studio и включить MCP в Assistant → Manage MCP Servers; проверить соединение с Codex, `list_roblox_studios`, `search_game_tree`, `execute_luau`, `start_stop_play`, `get_console_output`. Вызовы после выбора Studio должны передавать актуальный `studio_id`. При недоступности MCP использовать Rojo + обычный Playtest, записать блокер, не объявлять MCP работающим и не выдумывать команды Linux-обёртки. Приоритет официальный: https://create.roblox.com/docs/studio/mcp .

**Важное правило:** исходный Luau-код хранить в Git-репозитории и синхронизировать через Rojo. Изменения кода непосредственно в Studio по MCP нельзя оставлять единственной актуальной копией и нельзя перезаписывать Rojo без проверки. Сцены, модели и визуальные объекты могут создаваться через Studio/MCP с понятным процессом фиксации в проекте.

## 11.3. Граница клиент/сервер

**Сервер:** профиль, баланс, выдача предметов, аренда, репутация, генерация и жизненный цикл заказов, проверка выполненных шагов, распределение выплат, права на недвижимость, подарки.

**Клиент:** UI, ввод, локальные анимации, предпросмотр мебели, интерфейс мини-игр, звуки и визуальные эффекты.

Команды клиента — **запросы**, а не сообщения о свершившихся финансовых операциях. Сервер проверяет расстояние до объекта, участие в заказе, права доступа, последовательность шагов, лимиты скорости выполнения и типы данных. Данные сети минимальны и типизированы.

## 11.4. Сохранения и устойчивость

- Профиль игрока с версией схемы и понятными миграциями.
- Хранение денежных ресурсов, опыта, репутации, инвентаря, имущества, транспорта, конфигураций комнат, комплексных заказов и истории критических операций.
- Безопасные повторные попытки при временных ошибках, защита от конфликтующих сессий, идемпотентные награды и подарки.
- Нельзя создавать деньги или дублировать предметы из-за повторного RemoteEvent, переподключения или повторной записи.
- Нужна проверка сохранений на настоящей серверной сессии Roblox, не только на локальном UI.

## 11.5. Конфигурации данных [ПРЕДЛОЖЕНИЕ]

Предметы, профессии, этапы работ, типовые помещения, транспорт, цены, уровни доступа, строки UI и параметры заданий вынести в расширяемые таблицы конфигурации. Нельзя зашивать стоимость инструментов и продолжительность действий во множество независимых скриптов.

## 11.6. Наблюдаемость

Предусмотреть структурированные события: начало/конец обучения, предложение/принятие/завершение заказа, причину отказа от задания, покупку, смену жилья, применение мебели, ошибки сохранения, критические отклонения антиэксплойт-проверок. Не сохранять лишние персональные данные.

# 12. План выпуска и границы MVP

## 12.1. Вертикальный срез (первым делом)

**[УТВЕРЖДЕНО: 53-А]** Один небольшой участок города + бесплатная стартовая комната + приложение Jobs + **покраска как первая полностью рабочая профессия** + деньги + первая покупка/размещение предмета + сохранение. Камера третье лицо + контекстный рабочий ракурс. Цель: доказать, что цикл «работа → награда → улучшение жилья» интересен и стабилен. Подробная спецификация вертикального среза — разделы 16–19.

## 12.2. Функциональный MVP

- Один насыщенный район и ограниченный набор интерьеров.
- Четыре начальные профессии с поэтапными действиями.
- Генерация заказов на основе валидированных планировок и наборов объектов.
- Небольшое количество комплексных контрактов, доступных одному игроку.
- Бесплатное стартовое жильё + один вариант аренды/покупки с базовым редактором интерьера.
- Велосипед/самокат, аренда подходящего грузового транспорта, базовая физика машин.
- Внутриигровой телефон, английский и русский интерфейс.
- Общий опыт, профессиональный опыт, репутация.
- Надёжное сохранение и защита серверных операций.
- Совместные контракты и покупка подарков можно включать **после** устойчивой одиночной версии, чтобы не блокировать раннее тестирование.

## 12.3. После MVP

Покупка/улучшение мастерской, развитая система автомобилей, больше недвижимости и профессий, подарки из собственного инвентаря, сезонные события, коллекции, более развитый кооператив, специализации, дополнительные бытовые взаимодействия и расширение города.

## 12.4. Принцип «готово» для задач Codex

Любая завершённая функция должна иметь:

1. Реальное выполнение в Roblox Studio; не только компилирующийся скрипт.
2. Проверенные основные сценарии, ошибки ввода, повторные запросы и случаи выхода игрока.
3. Проверку мобильного управления и адаптации интерфейса там, где функция интерактивна.
4. Локализацию строк на английский и русский.
5. Отсутствие доверия клиенту при финансовых операциях.
6. Понятную документацию, настройки и воспроизводимую инструкцию теста.
7. Прохождение автоформатирования, статических проверок и доступных тестов.
8. Коммит в Git с понятным описанием; публикация/слияние в main — только после согласованного цикла проверки.

# 13. Приёмочные сценарии (первые обязательные тесты)

**AT-01. Первый заказ:** новый пользователь получает корректный заказ → добирается до него → выполняет все этапы → получает ровно одно начисление денег и опыта.

**AT-02. Защита выплат:** повторная отправка запроса завершения, неверная позиция и попытка подставить сумму награды не изменяют баланс.

**AT-03. Процедурность:** генератор на серии фиксированных seed создаёт только достижимые задания без отсутствующих предметов и циклов зависимостей.

**AT-04. Покраска:** клиент видит реальную смену покрытия стены и может завершить задание одинаково на мыши и телефоне.

**AT-05. Сборка:** этапы визуально изменяют предмет; неправильная деталь не превращается в успешный шаг.

**AT-06. Ремонт:** начинающий получает понятные подсказки; опытный — более сложную диагностику без искусственного увеличения времени ожидания.

**AT-07. Перевозка:** груз габаритно совместим с транспортом; загруженный предмет зафиксирован; выгрузка разрешена только в нужной точке.

**AT-08. Продолжение сложного заказа:** отключение и повторное подключение не дублирует денежные награды, сохранённые этапы доступны для продолжения.

**AT-09. Редактор интерьеров:** купить/установить/повернуть предмет → выйти → вернуться → расположение сохранено; посторонний игрок не может редактировать чужую комнату без разрешения.

**AT-10. Аренда:** отсутствие несколько суток не меняет счётчик аренды и не создаёт долг; по завершении аренды действует льготный период только онлайн, затем мебель безопасно переносится на склад и бесплатная комната остаётся доступна.

**AT-11. Кооператив:** двое игроков разделяют задачи; сервер считает подтверждённый вклад каждого; повторная приёмка не выплачивает награду повторно.

**AT-12. Подарки:** на первом этапе игрок может купить подарок только онлайн-участнику своего сервера; одна оплата → один полученный предмет; отказ/таймаут → контролируемый возврат; повторное подтверждение не выдаёт дубликат. Передача личных предметов и офлайн-доставка — отдельный будущий этап.

**AT-13. Мобильный UX:** во всех четырёх профессиях действия доступны без мелких интерактивных целей и пересечений с экранными кнопками перемещения.

**AT-14. Производительность:** профилирование на целевом слабом мобильном устройстве, стресс-тест сервера на 12–16 игроках; целевые бюджеты FPS/памяти определить после выбора минимальных устройств.

**AT-15. Выбор начального транспорта:** выбрать велосипед/самокат → получить ровно один транспорт → перезайти → выбор сохранился; при повторных запросах копии не создаются.

**AT-16. Камера:** начать покраску → камера приближается → прервать мини-игру/умереть/переподключиться → возвращается обычный режим без блокировки управления.

**AT-17. Размещение:** сетка и свободная установка работают; попытки установить мебель за пределами комнаты, в обязательном проходе или чужом помещении отвергаются сервером.

**AT-18. Лидерство:** при уходе лидера активная роль передаётся оставшемуся игроку, а при выходе всех комплексный заказ сохраняется в `Paused`.

# 17. Вертикальный срез P0: полный сценарий игрока

## 17.1. Цель и минимальная сцена

**Проверяемая гипотеза:** новичку нравится цикл `взять задание → подготовить стену → покрасить → получить награду → купить предмет → поставить предмет у себя → увидеть сохранённый результат`.

Необходимые объекты сцены:

- Небольшой безопасный игровой квартал (дорога, фасады, тротуар, вход в дом заказчика); детали можно добавить после проверки механик.
- Бесплатная личная комната общежития на основе одного шаблона (пока без перегородок), точка появления и доступный интерьер.
- Рабочая квартира заказчика на основе одного подготовленного шаблона с одной или двумя окрашиваемыми стенами.
- NPC/маркер клиента, доступная точка прибытия и интерактивный телефон с вкладками `Jobs` и `Home`.
- Каталог из **минимум одного** предмета декора/мебели, который можно приобрести за первую награду, превью и установка.
- UI: сумма денег, активный заказ, шаги работы, оценка результата, управление камерой и переключатель языка EN/RU.

В этой версии поездка на автомобиле и выбор транспорта **не блокируют** работу над P0: по кварталу можно дойти пешком. Выбор транспорта будет реализован в расширении сценария и должен учитывать принятое решение 59-В.

## 17.2. Onboarding

| Шаг | Действие игрока | Обязательный результат |
|---|---|---|
| 1 | Впервые входит | Создан профиль с уникальным UserId, показана бесплатная комната; интерфейс не завален окнами. |
| 2 | Открывает телефон | Видит `Jobs` и доступный обучающий заказ покраски. |
| 3 | Принимает заказ | Сервер закрепляет задание за игроком; появляется маркер маршрута. |
| 4 | Доходит до квартиры заказчика | Доступна только его рабочая зона; других игроков не пускают редактировать этот заказ. |
| 5 | Осматривает стену | Получает понятную задачу: требуемый цвет и подготовительные работы. |
| 6 | Подготавливает поверхность | Выполняет короткое действие, которое действительно меняет состояние стены/окружения. |
| 7 | Выбирает инструмент и краску | Проверяется соответствие заказу; ошибку можно исправить без катастрофического штрафа. |
| 8 | Красит поверхность валиком | Стена визуально меняется, виден прогресс по рабочей зоне, одинаково доступно мышью и свайпом. |
| 9 | Запускает проверку | Сервер вычисляет покрытие, соблюдение этапов и качество. |
| 10 | Сдаёт заказ | Деньги и XP начисляются **ровно один раз**; появляется краткий результат `до/после`. |
| 11 | Покупает мебель/декор | Сервер списывает деньги один раз и создаёт объект инвентаря; UI обновляется. |
| 12 | Размещает предмет дома | Валидное размещение сохраняется; предмет виден игроку. |
| 13 | Выходит и возвращается | Баланс, покупка, состояние профиля и размещение мебели восстановлены. |

## 17.3. Подробная мини-игра «Покраска»

**Фазы:** `Inspect → Prepare → ChooseMaterial → Paint → InspectResult → Submit`.

1. `Inspect`: камера мягко приближается к поверхности. Подсвечивается целевая стена, показываются требуемый цвет и шаги.
2. `Prepare`: для обучающего заказа игрок закрывает пол защитной плёнкой либо выполняет другое одно подготовительное действие. Сложный грунт/шпаклёвка не включаются в P0.
3. `ChooseMaterial`: игрок выбирает валик и нужный цвет из 2–3 образцов. Выбор неправильного образца сопровождается понятной подсказкой и возможностью исправления.
4. `Paint`: игрок ведёт валиком по стене. Сервер и клиент ведут дискретную карту покрытия поверхности. Клетки карты — **технические единицы учёта**, визуально покраска должна выглядеть плавнее грубой сетки.
5. `InspectResult`: система подсвечивает непрокрашенные участки; новичок может докрасить их и повторить проверку.
6. `Submit`: сервер подтверждает, что необходимые фазы завершены и минимальный порог покрытия достигнут. Результат фиксируется; выдаётся награда.

**Техническая гипотеза для P0:** карта покрытия `12 × 8` зон на одну прямоугольную стену (96 зон), порог завершения для новичка ~80%, наполнение с эффектом мягкого перехода. Эти числа **не утверждены**; определить по реальному тестированию. Нельзя жёстко привязывать UX к точному пикселю на смартфоне. Можно увеличить виртуальную область попадания пальца, сохранив правдоподобную визуализацию.

**Модель управления:**

- ПК: наведение/нажатие и перемещение мыши по рабочей поверхности; возможность прервать действие.
- Мобильный: свайп на большой активной поверхности; UI операций находится вне области управления движением и камерой; крупные кнопки действий.
- Камера: третье лицо в мире, рабочий контекстный ракурс в мини-игре, мягкий и гарантированный откат при завершении/отмене.

**Серверная валидация** — не доверять проценту покрытия или результату, вычисленному клиентом. Предлагаемый протокол: клиент отправляет ограниченные события начала/продолжения движения валиком с нормализованными координатами; сервер проверяет актуальный заказ, фазу, близость игрока к своей стене, выбранный материал, диапазон координат, частоту пакетов, реалистичную скорость покрытия и собственную сетку прогресса. Изображение стены и эффекты могут прорисовываться локально для плавности. Клиент **не** отправляет итоговую сумму награды.

**Ограничения защиты от эксплойтов:** сервер не может достоверно доказать наличие реального движения пальца/мыши. Поэтому защищаем значимые последствия (скорость прогресса, доступность зоны, порядок этапов, выплата), а не обещаем идеальную детекцию внешнего автокликера. При сомнительных событиях отклонять шаг без списания денег.

**Качество** рассчитывается по выполнению этапов, соответствию цвета и покрытию; новичку даются повторные попытки и подсказки. Ошибки не должны превращать обучение в штрафной режим.

## 17.4. Тестовые суммы (только для вертикального среза)

Чтобы можно было пройти первый цикл, Codex вправе использовать **временные тестовые значения**, вынесенные в конфигурацию:

- стартовый баланс: `$0`;
- первая покраска: базовая выплата `$250`;
- первый декоративный предмет: `$180`;
- учебный заказ занимает ориентировочно `3–5 минут` вместе с перемещением и подсказками.

Это тестовые значения для доказательства цикла, а не итоговая экономика. После игрового теста необходимо собрать фактическое время выполнения и пересчитать баланс. Не встраивать эти числа в код UI или отдельных инструментов.

## 17.5. Минимальный редактор обустройства комнаты

Для P0 обязательно реализовать:

- каталог с уникальными `itemId` и понятными ценами;
- инвентарь с уникальными `instanceId` покупок;
- переключаемые **режим сетки / свободная установка** (свободный режим допускает дискретизацию с небольшим шагом для сетевой и серверной надёжности);
- предпросмотр с зелёным/красным состоянием, поворот предмета, подтверждение/отмена;
- размещение только собственных предметов в собственной комнате и только в допустимой зоне;
- сохранение позиции и угла предмета в координатах **шаблона комнаты**, а не абсолютных мировых координатах;
- восстановление после переподключения.

Перегородки, двери, смена текстур стен и этажей — требования полного редактора, но **не блокируют P0**. Для них проектируется отдельный валидатор топологии помещения: не трогать внешние и несущие конструкции, сохранять проходы, точки входа и пути эвакуации в игровом смысле.

Не хранить CFrame/Instance непосредственно: сохранять сериализуемые числа и IDs. `recentOperations` должен иметь ограничение по размеру, а награда текущего заказа — устойчивый признак обработки, не зависящий только от очищаемого кольцевого журнала.

## 18.3. Контракт заказа (пример)

```lua
JobRecord = {
  jobId = "job-unique-id",
  templateId = "paint-small-room-v1",
  seed = 123456,
  locationId = "Apartment_01",
  ownerUserId = 123456,
  status = "Accepted", -- Accepted / InProgress / ReadyForInspection / Completed / Cancelled
  revision = 1,
  currentStep = "Inspect",
  painting = {
    wallId = "Wall_A",
    requiredColorId = "warm-white",
    completedSteps = {},
    coverage = {}, -- компактное сериализуемое состояние, если сохраняется
    elapsedValidatedSeconds = 0,
  },
  rewardOperationId = nil,
}
```

В полном генераторе добавить DAG этапов, стоимость материалов, условия заказчика и проверенные вклады кооператива. Генерация/seed — серверные; клиенту отдавать только сведения, необходимые для UI и игрового взаимодействия.

## 18.4. Разрешённые намерения клиента

| Команда | Вход клиента | Основная проверка сервера |
|---|---|---|
| `RequestAvailableJobs` | фильтр/страница | допустимые фильтры; ограничение частоты |
| `AcceptJob` | `jobOfferId` | доступность, уровень, отсутствие конфликта заданий |
| `StartWorkStep` | `jobId`, `stepId`, `targetId` | правильная зона, активный шаг, расстояние, доступные инструменты |
| `SubmitPaintStroke` | `jobId`, `wallId`, нормализованные координаты | границы, валидная фаза, скорость прогресса, лимит пакетов |
| `InspectWork` | `jobId` | все обязательные этапы проверены сервером |
| `SubmitJob` | `jobId` | готовность, однократность выплаты |
| `PurchaseItem` | `catalogItemId` | цена **из серверного каталога**, баланс, допустимость предмета |
| `PreviewPlacement` | локальное действие (без серверной выплаты) | клиентский превью; окончательная проверка — только при фиксации |
| `PlaceItem` | `instanceId`, относительная позиция/угол | владение, границы, поверхность, коллизии, права |
| `CancelWork` | `jobId` | возврат камеры, завершение текущей сессии работы без денежного штрафа за отключение |

**Запрещено:** принимать от клиента `wallet`, `reward`, `isCompleted`, `ownerUserId` и другие авторитетные значения как истинные. Сервер проверяет типы, лимиты строк/таблиц, `NaN`/бесконечности, повторы, частоту и последовательность действий. Именование вызовов — проектный пример, а не готовый Roblox API.

## 18.5. Постоянное хранение

- При входе загружать профиль и удерживать владение активной сессией; при конфликтующем входе не перезаписывать более свежую версию без согласования.
- В ходе игры изменять серверную копию профиля, сохранять на контрольных точках и периодически с разумным интервалом.
- Для конкурентно обновляемых данных применять `UpdateAsync()` с обработкой ошибок/повторных попыток; не перезаписывать свежие данные устаревшим состоянием после сетевой ошибки.
- Награда за заказ и соответствующий признак `Completed` / `rewardOperationId` должны сохраняться согласованно **в одной записи профиля**, чтобы при повторной обработке не начислить сумму второй раз.
- При временной ошибке загрузки не запускать игрока в «пустом профиле с возможностью покупки»; показывать безопасное сообщение/повторную попытку.
- `BindToClose` и выход игрока: попытаться корректно сохранить; нельзя объявлять функциональность надёжной без проверки ошибок и аварийного завершения сервера.
- Количество запросов к DataStore нужно держать в рамках квот; не сохранять каждый пиксель движения валиком отдельной записью.

Дальнейшее расширение потребует отдельного протокола межпрофильных подарков: `escrow / pending / accepted / delivered / refunded` с восстановлением после неизвестного исхода записи, без выдуманной атомарности между профилями.

## 19.2. Этап 1 — профиль, сцена, UI

- Сцена стартовой комнаты и комнаты заказчика; спавн, безопасная навигация, базовая камера.
- Начальный профиль, серверная экономика, телефон (`Jobs`, `Home`), английская/русская локализация.

## 19.3. Этап 2 — покраска

- Один обучающий шаблон, выдача задания через Jobs.

- Минимум один вариант отличающегося задания после обучения (цвет/стена/условие).
- Playtests на ПК и в мобильном эмуляторе Studio, затем при возможности на реальном смартфоне.

## 19.4. Этап 3 — магазин и комната

- Каталог, покупка, единственный предмет инвентаря, режим сетки/свободного размещения, проверка прав, сохранение и повторная загрузка.
- Данные позиции хранить относительно комнаты, чтобы объект не менял место при переносе экземпляра комнаты на другой участок мира.

## 19.5. Этап 4 — качество и доказательство устойчивости

- Проверить весь сценарий из раздела 17.2 в одной сессии и после повторного входа.
- Отключение во время покраски: без отрицательного баланса/штрафа, без застрявшей камеры; для P0 обычный незавершённый заказ допускается отменять.
- Повторная отправка `SubmitJob`: не создаёт второй выплаты.
- Подмена стоимости покупки/передача вымышленного `itemId`: сервер отклоняет.
- Размещение предмета за пределами комнаты/в чужой комнате: отклоняется.
- Симуляция потерь/задержек RemoteEvent: нет ошибок состояний, бесконечных анимаций, дублированных предметов.
- Проверить UI с разными экранными разрешениями и сенсорным управлением; центр рабочей зоны не перекрыт кнопками.
- Проверить ошибки в консоли, статический анализ, форматирование, отчёт о тестах.

## 19.6. Gate готовности P0

P0 считается выполненным только когда:

1. Новый игрок самостоятельно проходит весь сценарий от получения работы до установки мебели.
2. Реально работающая мини-игра покраски меняет визуальное состояние стены; это не один таймер «удерживай E».
3. Выплата и покупка выполняются **только сервером** и защищены от повторного начисления/дублирования.
4. Деньги, предмет и его положение переживают выход и повторный вход.
5. Управление и интерфейс проверены как минимум в PC и mobile emulator, с подтверждением или зафиксированными блокерами реальных устройств.
6. Проверки проекта проходят; есть воспроизводимые команды сборки и запуска.
7. Codex предоставил краткий отчёт: что реализовано, что протестировано, какие риски/ограничения остались. Отсутствие работающего MCP не должно скрываться.

## 19.7. Что НЕ входит в P0

Покупка полноценного автомобиля, транспортные потоки NPC, все четыре профессии, комплексные задания, совместная работа, подарки, аренда недвижимости, изменение перегородок, мастерская, сезонные события и магазин за Robux. Эти функции сохраняются в **общем GDD**, но не должны блокировать доказательство базового цикла.

# 23. Игровая сцена P0: состав объектов и маршрут игрока

## 23.1. Цель вертикального среза

**Один действительно рабочий проход без заглушек:** стартовая комната → приложение Jobs → заказ покраски → путь до дома клиента → подготовка и покраска → приёмка → награда → каталог предметов → установка мебели → повторный вход с сохранённым результатом.

Не превращать P0 в шаблон пустого Tycoon: визуальная смена стены и реальное размещение мебели — обязательные признаки работающей механики.

## 23.2. Обязательные пространства

| ID в проекте | Назначение | Минимальный состав | Принадлежность |
|---|---|---|---|
| `StarterDormTemplate_v1` | Бесплатная комната игрока | Пол, 4 стены, вход, освещение, место для мебели, SpawnPoint | Персональная собственность/право игрока, бессрочно |
| `StreetBlock_P0_v1` | Маршрут и атмосфера | Тротуар, дорога, фасады, освещение, указатели, здание клиента | Общий игровой мир |
| `ClientApartment_Paint_v1` | Рабочее помещение | Вход, NPC/маркер, 1–2 интерактивные стены, подготовительное действие | Назначенный контракт/доступ участника |
| `FurnitureShop_P0_v1` | Первая покупка | Магазин либо киоск + каталог с ценами | Общий игровой мир; покупки частные |
| `HomeEntrance_P0_v1` | Возврат домой | Физический вход из улицы/коридора | Только переход, не постоянный рендер всех комнат |

**Рекомендуемая компоновка P0:** помещения находятся достаточно близко, чтобы игрок мог завершить маршрут пешком без транспорта. Велосипед/самокат остаются обязательными для более позднего MVP, но их отсутствие не блокирует первый тест покраски. Фасады и улицу строить из повторно используемых модулей, не тратить первый этап на большой город.

## 23.3. Состояния мира

- Первая загрузка: игрок появляется в своей комнате, телефон доступен, на карте выделена только одна учебная работа.
- При принятии заказа: выбранный объект отмечается навигацией; произвольные квартиры и их интерьеры не открываются автоматически.
- В рабочей квартире: только подписанные на контракт игроки получают права на рабочие действия; остальные могут видеть обычную окружающую сцену, но не менять задания.
- После сдачи: отремонтированная стена остаётся в завершённом виде на время демонстрации результата. Новое задание создаёт новый **экземпляр состояния** или сбрасывает подготовленный объект в своей изолированной рабочей зоне, не портя прогресс другого игрока.
- Возврат домой: предмет из инвентаря размещается только в разрешённой геометрии личной комнаты.

# 24. UX-спецификация P0: экраны, состояния, адаптивность

## 24.1. Принципы [УТВЕРЖДЕНО + ПРЕДЛОЖЕНИЕ]

- Минималистичный игровой HUD; основные действия через виртуальный телефон.

- Модальные окна закрываются явной кнопкой; отмена действия не приводит к блокировке камеры/инвентаря.

## 24.2. Экранные состояния

## 24.5. Mobile UX — обязательные испытания

- Тестировать несколько пропорций экрана, включая узкие и широкие дисплеи, с визуальным контролем вырезов/верхней панели Roblox.
- Проверять жест покраски, когда стандартные мобильные кнопки движения активны; в рабочем режиме можно временно **заморозить перемещение персонажа**, но камера обязательно восстанавливается после выхода.
- При изменении ориентации/размера экрана не терять выбранный заказ, предмет и состояние покупки; верстка пересчитывается.
- Если камера сфокусирована на стене, панель действий должна смещаться вне зоны жеста; обязательные кнопки — в safe area.
- Не требовать одновременного свайпа и удержания второй кнопки для завершения простой работы.
- Экран покраски должен работать без мыши; эмулятор Studio — минимальная проверка, реальный телефон — обязательная проверка до выпуска, если доступен.

# 25. Интерактивное обучение при первом заказе [УТВЕРЖДЕНО: 61-Б]

## 25.1. Сценарий на реальной миссии

**Цель:** игрок самостоятельно принимает первый заказ, узнаёт базовые элементы HUD и телефона, заканчивает простую покраску и покупает предмет для комнаты. Подсказки появляются в момент действия; долгого отдельного обучающего мира нет.

| State | Триггер | Подсказка | Признак выполнения |
|---|---|---|---|
| `INTRO` | Первый вход в игру | «Это твоя комната. Открой телефон, чтобы найти работу» | Телефон открыт |
| `JOB_LIST` | Вкладка Jobs | «Выбери первый заказ» | Карточка выбрана |
| `ACCEPT` | Детали заказа | «Прими заказ, чтобы увидеть маршрут» | Сервер выдал jobId |
| `NAVIGATE` | Заказ принят | «Следуй к отмеченному дому» | Игрок подошёл к входу |
| `INSPECT` | Вход в рабочую комнату | «Осмотри стену» | Сервер зафиксировал осмотр |
| `PREPARE` | Осмотр завершён | «Подготовь поверхность» | Подготовительный шаг завершён |
| `PAINT` | Инструмент выбран | «Проводи валиком по стене» | Валидировано требуемое покрытие |
| `SUBMIT` | Работа принята | «Заверши заказ» | Сервер начислил награду один раз |
| `BUY` | Появился результат | «Выбери предмет для комнаты» | Покупка подтверждена |
| `PLACE` | В личной комнате | «Поставь предмет там, где нравится» | Предмет размещён сервером |
| `DONE` | Размещение сохранено | «Готово. Дальше решаешь сам!» | `onboarding.completed=true` |

## 25.2. Пропуск, повторный вход, ошибки

- Не блокировать свободное исследование города длинными заставками. Подсказки можно скрывать, но учебный заказ остаётся доступным.
- Не показывать пройденные обучающие сообщения повторно после выхода/возврата; хранить **компактный** прогресс обучения в профиле. Внутри заказа восстановление допускается на безопасной контрольной точке.
- При перезагрузке приложения/смерти персонажа сбрасывать временные эффекты и рабочую камеру; серверное состояние задания остаётся корректным.
- Если данные игрока не загрузились, не показывать фальшивые «нулевой баланс/первый заказ» как успешный вход.
- Для будущих персонажей другого уровня учебные подсказки можно открыть повторно в настройках, но не навязывать.

# 26. Мини-игра «Покраска»: подробный инженерный контракт

## 26.1. Цель

Работа должна ощущаться тактильно: игрок **сам перемещает валик**, видит покрытие прямо на стене, слышит реакцию инструмента и может исправить пропущенные участки. Одного таймера с кнопкой `Hold to finish` недостаточно.

## 26.2. Объект `PaintableWall`

| Поле | Значение / смысл |
|---|---|
| `wallId` | Стабильный ID стены внутри шаблона |
| `templateVersion` | Версия геометрии/настройки поверхности |
| `surfaceSize` | Ширина/высота окрашиваемой области |
| `allowedMaterialIds` | Цвета/покрытия, доступные в этом задании |
| `coverageGrid` | Компактная серверная карта сегментов, **для P0 тестировать 12×8** |
| `jobInstanceId` | Какая работа контролирует эту поверхность |
| `phase` | Prepared/Painting/Ready/Accepted |
| `visualState` | Состояние визуализации для клиента, не источник прав на награду |

При генерации заказа wallId должен ссылаться на реально существующую поверхность с определёнными нормалью, размером и ограничениями взаимодействия. Важно не путать `surfaceId` и произвольный Instance, переданный клиентом.

## 26.3. Порядок выполнения

1. Сервер назначает игроку заказ и создаёт `jobInstanceId`.
2. Игрок входит в рабочую комнату, осматривает стену (соответствующий шаг заказа активируется сервером).
3. Выполняет подготовку: защитить пол/подготовить зону (в P0 одно простое интерактивное действие).
4. Выбирает валик и запрошенный цвет. Сервер подтверждает инструмент и материал.
5. Клиент переключает камеру в рабочий режим, показывает валик и локально визуализирует след движения.
6. Игрок ведёт валик по проекции поверхности; клиент отображает реакцию сразу, **не дожидаясь сети**.
7. Клиент отправляет небольшими пакетами данные о нормализованных координатах и последовательности жестов.
8. Сервер ограничивает частоту сообщений, проверяет участие, геометрию, последовательность, валик и допустимую скорость покрытия; пересчитывает авторитетную карту и подтверждает состояние.
9. При проверке сервера недокрашенные участки подсвечиваются; новичок может исправить без значительного наказания.
10. После приёмки сервер фиксирует одно завершение и одну награду; клиент показывает результат.

## 26.4. Передача мазков по сети [ПРЕДЛОЖЕНИЕ]

Пример **логической** структуры события, не готовая Luau-функция:

```lua
StrokeBatch = {
  jobId = "job-id",       -- активный серверный jobId
  wallId = "wall-a",      -- только известный wallId назначенной работы
  sequence = 14,          -- монотонный номер пакета
  points = {              -- ограниченная длина; координаты 0..1 по поверхности
    {u = 0.23, v = 0.44},
    {u = 0.25, v = 0.48},
  },
}
```

**Обязательные проверки:**

- Профиль и заказ действительны; игрок находится в правильном рабочем помещении в разумном радиусе стены.
- Текущая фаза позволяет красить; подготовка и выбор материалов подтверждены сервером.
- `sequence` не обработан ранее; слишком старые, повторные, громадные и некорректные пакеты отклоняются.
- Координаты конечны и лежат в пределах поверхности. Строки, размеры таблиц, количество точек ограничены.
- Сервер самостоятельно интерполирует путь в допустимых пределах и отмечает клетки покрытия по известному радиусу валика. Не верить полю `completionPercent` от клиента.
- Есть лимиты максимальной скорости закрытия площади и объёма команд за единицу времени. **Начальные настройки** — в конфигурации, калибровать на устройствах; не считать, что сервер может достоверно установить физическое движение пальца.
- Визуальные мелкие частицы/анимации не должны создавать один RemoteEvent на каждый кадр или каждую каплю.

**Сетевой подход P0:** сгруппировать движения вместо передачи каждого пикселя/кадра; клиент мгновенно показывает локальный след, сервер периодически сообщает компактное подтверждённое состояние. Повторные пакеты не увеличивают покрытие/выплату. При разнице между клиентом и сервером аккуратно синхронизировать отображение без резкого «перекрашивания назад» там, где это возможно.

## 26.5. Помощь игроку и визуализация [УТВЕРЖДЕНО: 63-В]

- У зоны касания есть увеличенный допуск для пальцев; валик может мягко «примагничиваться» к краю доступной области.
- Если остались небольшие щели между сегментами, применять безопасное локальное сглаживание/расширение следа до соседних сегментов. Помощь не должна окрашивать всю стену от одного жеста.
- При запросе проверки подсветить оставшиеся зоны с понятной инструкцией; не требовать идеального ручного покрытия углов.
- Звук контакта с поверхностью, небольшая анимация движения инструмента, видимый цветовой след и короткая обратная связь при завершении.
- Плавное визуальное покрытие может реализовываться SurfaceGui/маской/готовыми слоями, если профилирование позволяет; способ рендеринга не зафиксирован и должен быть подтверждён работающим прототипом в Studio, а не выбран ради эффекта на бумаге.
- На слабых устройствах отключать дорогие частицы, оставляя ясную анимацию покрытия. **Результат работы должен быть читаем даже без эффектов.**

## 26.6. Оценка качества

Для начинающего мастера обязательны: валидный цвет, подготовительный шаг, достижение порога покрытия и явная приёмка работы. При ошибке можно исправить цвет/пропуски без полной перезаписи заказа. Штрафы на первых уровнях минимальны. Величины порога (~80% для P0), визуального сглаживания и награды настраиваются, но не считаются утверждёнными.

## 26.7. Сбои и выходы

- Отмена до сдачи: нет оплаты и сурового штрафа; камера и управление восстанавливаются.
- Смерть/респавн: локальная мини-игра закрывается; сервер не принимает мазки от предыдущей сессии работы.
- Дисконнект: для обычного заказа P0 допустима отмена или восстановление из ближайшей безопасной точки без денежного штрафа; сложные проекты позднее обязаны сохраняться.
- Повторная сдача: возвращает тот же итоговый результат, **не** повторную награду.

# 27. Личная комната и редактор интерьера: подробный P0

## 27.1. Сценарий

Игрок впервые входит в бесплатно предоставленную комнату, зарабатывает деньги и приобретает предмет. Открыв `Home` или взаимодействуя с комнатой, он может выбрать предмет и поставить его в одном из разрешённых мест. После повторного входа предмет остаётся там же.

## 27.2. Каталог P0 [ПРЕДЛОЖЕНИЕ]

Для проверки UI и размещения предложить 3–5 предметов разного типа: настольная лампа, стул, растение, небольшой шкаф, коврик. Один предмет должен быть доступен на награду за первый заказ. У каждого предмета — `catalogItemId`, цена, модель и версия ассета, занимаемая площадь, допуски установки (`floor`, `wall`, `table`), описание и локализованное имя.

**Важное различие:** покупка создаёт принадлежащий игроку **экземпляр предмета** `itemInstanceId`, а не «покупает» физическую модель из общего мира. Модель комнаты создаётся из этого экземпляра только при загрузке комнаты.

## 27.3. Операции режима строительства

| Операция | На клиенте | На сервере |
|---|---|---|
| Выбрать предмет | Подсветить карточку инвентаря | Подтвердить владение при применении |
| Переместить | Полупрозрачное превью с Raycast/поверхностью | Подтвердить конечное положение |
| Повернуть | Плавный/пошаговый предпросмотр | Ограничить допустимый угол/габариты |
| `Grid` | Привязка к сетке по параметрам конфигурации | Проверить итоговую геометрию |
| `Free` | Плавное позиционирование без привязки | Проверить итоговую геометрию |
| Установить | Показать ожидаемое место | Проверить собственность, границы, коллизии, проходы, затем сохранить |
| Убрать в инвентарь | Скрыть модель после подтверждения | Снять размещение, **не уничтожить купленный предмет** |
| Отменить | Вернуть исходное превью | Ничего не списывать и не менять |

**Режим `Grid/Free` утверждён ранее (55-В).** Изменение перегородок и дверей в полноценном редакторе утверждено (19-Б), но **не включается в P0**.

## 27.4. Границы и сохранения

- Позиции предметов сохранять относительно координат версии шаблона комнаты (локальная позиция + поворот), а не мировым CFrame как абсолютной координатой.
- Блокировать установку вне комнаты, внутри запрещённых объёмов, в проходе, на некорректной высоте, поверх другого несовместимого предмета; сервер должен проверять реальную модель/объём.
- Входы, точки появления и минимальные коридоры движения задаются как `ReservedVolumes`, защищённые от загромождения. P0 не требует полного пересчёта навигационной сетки на каждом движении предмета.
- У операции установки есть ID и версия состояния комнаты, чтобы повторная отправка запроса или сетевые задержки не создали две модели из одного предмета.
- При изменении каталога старые `catalogItemId` должны обрабатываться миграцией или безопасным fallback без исчезновения купленного имущества.
- До успешной загрузки профиля режим строительства недоступен.

# 28. Персональные интерьеры и система посещений [УТВЕРЖДЕНО: 62-В, 65-Б]

## 28.1. Видимость дома и фактический доступ

С улицы игрок видит общий дом и настоящий вход/подъезд. После взаимодействия сервер определяет, какую квартиру можно открыть, проверяет права и помещает игрока в личный **экземпляр интерьера** владельца. У посетителя нет права автоматически брать, продавать или двигать чужие вещи.

**Предлагаемая реализация после P0:** при входе на сервере выделяется изолированная рабочая ячейка/пространство для интерьера, клонируется подготовленный шаблон и на него накладывается сохранённая расстановка владельца. Владелец и допущенные гости перемещаются в один экземпляр. По завершении посещений и безопасной выгрузке экземпляр освобождается. Ограничить число одновременно активных интерьеров по результатам профилирования. Это не означает обязательного выделения отдельного Roblox-сервера на каждую квартиру.

**Граница приватности:** визуальная разобщённость комнат, физические границы и доступ к ним обеспечиваются сервером. Одного скрытия двери на клиенте недостаточно.

## 28.2. Режимы доступа

| Режим | Кто может войти | Проверка |
|---|---|---|
| `Private` / Закрыто | Только владелец | `visitorUserId == ownerUserId` |
| `Friends` / Друзья | Владелец + подтверждённые друзья Roblox | Серверная проверка отношений |
| `InviteOnly` / По приглашению | Владелец + явно приглашённые пользователи | Серверный список временных приглашений |
| `Public` / Открыто | Любой игрок этого сервера, пока владелец разрешает | Статус комнаты, вместимость, общие ограничения |

**Моя рекомендация (не ответ пользователя):** режим по умолчанию — `Private`. Приглашения и гостевой список не должны превращаться в публичное раскрытие персональных данных. Доступность друга между серверами и офлайн-приглашения — отдельная функциональность, не требуемая в первой версии посещений.

## 28.3. Права гостей и владельца

| Действие | Владелец | Гость |
|---|---|---|
| Посетить комнату | Да | При разрешении режима |
| Сесть, посмотреть декор | Да | Да, если предмет интерактивен |
| Покупать в свой инвентарь | Да | Да, вне контекста чужого имущества |
| Перемещать мебель владельца | Да | Нет |
| Продавать/передавать чужой предмет | Нет (если не владелец предмета) | Нет |
| Сменить правила доступа | Да | Нет |
| Выгнать гостя/закрыть доступ | Да | Нет |

При смене `Public → Private` уже находящимся гостям можно дать короткое уведомление и безопасно переместить их к выходу. Зависшие гостевые сессии не должны удерживать чужой профиль в блокировке записи. Система должна корректно обрабатывать выход хозяина, выход гостя и смерть/респавн персонажа.

## 28.4. Команды (логический контракт)

```text
SetPropertyAccess(propertyId, policy)    -> владелец, допустимая политика, сохранение
RequestVisit(propertyOwnerUserId)        -> право, вход, вместимость, создание/поиск инстанса
InviteVisitor(targetUserId)              -> хозяин онлайн, лимит приглашений, срок действия
AcceptVisitInvite(inviteId)              -> адресат, актуальность, место на сервере
LeaveInterior()                          -> безопасный телепорт к выходу, освобождение прав
KickVisitor(targetUserId)                -> только владелец, адресат — текущий гость
```

Названия — проектные, не API Roblox. Ни одно действие клиента не считается подтверждением права собственности или дружбы; право вычисляет сервер.

# 29. Аватар, одежда и взаимодействие с NPC [УТВЕРЖДЕНО: 60-В]

- По умолчанию загружать пользовательский Roblox-аватар и привычное управление Roblox. Не заменять его единым заранее созданным персонажем без необходимости.
- Для профессий использовать рабочие инструменты и анимации, совместимые с выбранным типом аватара; на этапе P0 проверить анимацию движения валика на стандартном современном персонаже.
- Игровая одежда и рабочая форма — предметы **внутриигрового каталога**, а не гарантированная покупка предметов Roblox Marketplace для всего аккаунта.
- После покупки игрок может надевать/снимать игровой комплект; его Roblox-аватар возвращается к исходному внешнему виду при снятии формы. Предмет одежды хранится в собственном инвентаре и не теряется при смене работы.
- Стартовый P0 не обязан содержать магазин одежды: он должен корректно отображать стандартный аватар и работать с его анимацией.
- NPC заказчика в первом прототипе может иметь фиксированный внешний вид, короткие локализованные реплики и несколько понятных анимаций; развитая система диалогов не нужна.

# 30. Данные профиля, сетевые команды и права [РАСШИРЕНИЕ раздела 18]

## 30.1. Дополнительные поля версии схемы

Пример будущего расширения профиля (конкретную версию схемы и миграцию определить при внедрении):

```lua
profile = {
  schemaVersion = 2,
  onboarding = {
    step = "INTRO",
    completed = false,
    seenHints = {},
  },
  avatar = {
    activeOutfitItemId = nil, -- внутриигровая одежда, не внешний Roblox Asset ID
  },
  properties = {
    homeRoomId = "Dorm_A",
    visitPolicy = "Private",
    furniturePlacements = {},
  },
  navigation = {
    -- текущая цель для UI может быть только временным состоянием сессии,
    -- не нужно записывать её в DataStore при каждом перемещении.
  },
}
```

**Пояснение:** это расширение схемы раздела 18.2, а не второй параллельный профиль. В реальном коде **единая** структура версии + функции миграции; не заводить `properties` и `property` как независимые истинные данные. Профиль нельзя перезаписывать дефолтом при неудачной загрузке.

## 30.2. Команды нового интерфейса

| Интент | Необходимость в P0 | Проверки |
|---|---|---|
| `GetJobsPage` | Да | Пагинация и допустимые фильтры |
| `SelectNavigationTarget` | Да | Цель реально видима/доступна игроку |
| `GetShopCatalog` | Да | Серверный каталог с ценами; read-only представление |
| `PurchaseCatalogItem` | Да | Серверная стоимость, остаток денег, уникальная операция |
| `SetPlacementMode` | Только локально | Состояние UI, сервер не доверяет невозможным трансформациям |
| `CommitPlacement` | Да | Владелец, один itemInstanceId, корректное размещение, ревизия комнаты |
| `SaveOnboardingProgress` | Нет как клиентская награда | Сервер отмечает шаг по факту валидного действия |
| `PurchaseOutfit` / `EquipOutfit` | После P0 | Владение/каталог/разрешённая форма |
| `SetPropertyAccess` | После P0 | Владелец, допустимый режим |
| `RequestVisit` / `InviteVisitor` | После P0 | Проверка доступа, срока и вместимости |

**Не создавать дублирующие remotes** с различными именами для одной операции (`GetJobsPage` vs `RequestAvailableJobs` из раздела 18). При реализации выбрать единый нейминг и описать его в `docs/network-contracts.md`.

## 30.3. Инварианты безопасности

1. Награды начисляются не более одного раза на уникальный `jobId`.
2. Покупка/установка/возврат предмета не должны делать две копии предмета или удалять оплаченный экземпляр.
3. Гостевые права не наследуют автоматически редакторские права владельца.
4. Клиент не выбирает произвольный `UserId` владельца как основание для телепортации или изменения чужой недвижимости.
5. Невалидные действия (скрипты удалённого пользователя, удалённые стены, NaN/Inf, повторные транзакции) безопасно отклоняются, не портя профиль.
6. Выход, респавн и закрытие интерфейса освобождают локальные блокировки камеры, ввода, анимаций и объектов управления.
7. Незавершённая обычная работа не приводит к крупному штрафу за отключение; комплексный заказ после его внедрения сохраняет проверенные этапы.

# 31. План задач Codex для первого вертикального среза

План задаёт последовательность **проверяемых задач**. Codex обязан держать рабочий проект после каждого принятого этапа; не заменять недоступный функционал фиктивными экранами.

| Ticket | Задача | Результат / критерий приёмки |
|---|---|---|
| `ENV-01` | Проверить Studio/MCP на Ubuntu/Vinegar | Реальный вывод проверки, лог/скрин Playtest; либо честно задокументированный блокер и Rojo fallback |
| `CORE-01` | Роутинг модулей, Rojo, статические проверки, Git | Воспроизводимая сборка, форматирование, статический анализ без ошибок в изменённом коде |
| `DATA-01` | Профиль, сериализация, миграция, серверная экономика | Правильный вход/выход, блокировка проблемного профиля, отсутствие повторной выплаты |
| `WORLD-01` | Минимальный участок, комната общежития, квартира клиента, магазин | Игрок проходит всю сцену пешком; точки и входы достижимы |
| `UX-01` | HUD, телефон, Jobs, Map + указатель, EN/RU, onboarding | Первый заказ принимается без непонятных интерфейсных тупиков; HUD не перекрывает центр экрана |
| `PAINT-01` | State machine, валик, покрытие, эффекты, серверная валидация | На ПК и mobile emulator игрок действительно красит стену, а сервер проверяет этапы |
| `ECO-01` | Сдача заказа, награда, журнал идемпотентности | Одна работа — одна выплата; повторы и подмена данных не создают денег |
| `HOME-01` | Магазин, инвентарь, сетка/свободно, server commit | Первый оплаченный предмет устанавливается только владельцем, без коллизий |
| `SAVE-01` | Сохранение и возврат | Баланс, заказ, купленный и установленный предмет корректны после перезахода |
| `QA-01` | End-to-end и негативные тесты | Нет блокирующих ошибок, воспроизводимый отчёт ПК/mobile, зафиксированы исключения и оставшиеся риски |

## 31.1. Порядок выполнения

1. После каждого изменения собирать Rojo и запускать StyLua/Selene и доступные тесты.
2. При доступном MCP запускать Studio Playtest, проверять дерево и консоль; любые результаты записывать, а не просто утверждать «тесты прошли».
3. Если MCP на Ubuntu/Vinegar не подключён, использовать надёжный путь Studio + Rojo и не блокировать всю разработку на попытках недокументированной интеграции.
4. Для каждых 1–2 пользовательских функций — короткий ручной тест на мыши и touch emulator.
5. Зафиксировать PR/коммит, регрессионные тесты и список известных ограничений.

## 31.2. Условие «функция готова»

Каждая реализованная функция имеет: явный сценарий ввода → видимое изменение состояния → серверную авторитетную проверку → сохранение, если это прогресс/имущество → проверку отказа/повтора → тест на экране телефона, если имеет UI → обновление соответствующего `docs/*.md`.
